# N+1 Query Problem in JPA / Hibernate

## What is the N+1 Problem?

The N+1 problem occurs when Hibernate executes:

- 1 query to fetch a list of parent entities
- N additional queries to fetch related child entities one by one

Instead of fetching data efficiently in a single query, Hibernate fires multiple unnecessary queries.

## Example Scenario

Consider two entities:

```
Department
    |
    |
    |---- Employees
```

### Department Entity

```java
@Entity
public class Department {

    @Id
    private Long id;

    private String name;

    @OneToMany(mappedBy = "department")
    private List<Employee> employees;

}
```

### Employee Entity

```java
@Entity
public class Employee {

    @Id
    private Long id;

    private String name;

    @ManyToOne
    private Department department;

}
```

## Problematic Code

Fetching departments:

```java
List<Department> departments =
        departmentRepository.findAll();

for (Department dept : departments) {

    System.out.println(
        dept.getEmployees().size()
    );

}
```

Assume database contains:

```
Department table

ID    Name
------------
1     IT
2     HR
3     Finance
```

Each department has employees.

## Queries Generated

First query:

```sql
SELECT *
FROM department;
```

Result:

```
IT
HR
Finance
```

Then Hibernate executes:

```sql
SELECT *
FROM employee
WHERE department_id = 1;
```

```sql
SELECT *
FROM employee
WHERE department_id = 2;
```

```sql
SELECT *
FROM employee
WHERE department_id = 3;
```

Total queries:

```
1 + N
```

For 100 departments:

```
1 + 100 = 101 queries
```

This is the N+1 problem.

# Why Does It Happen?

Because of lazy loading.

Example:

```java
@OneToMany(
    mappedBy = "department",
    fetch = FetchType.LAZY
)
private List<Employee> employees;
```

`LAZY` means:

```
Load Department
        |
        v
Do not load Employees
        |
        v
Load Employees only when accessed
```

When code calls:

```java
dept.getEmployees()
```

Hibernate fires another query.

# Solutions to Avoid N+1

Common approaches:

1. Fetch Join
2. EntityGraph
3. DTO Projection
4. Batch Fetching

The most commonly used in Spring Data JPA are:

- EntityGraph
- DTO projections

# Solution 1: EntityGraph

## What is EntityGraph?

`EntityGraph` tells Hibernate:

> Fetch these relationships together when loading the entity.

Instead of relying on default lazy loading, we explicitly specify what associations should be fetched.

## Using @EntityGraph

Repository:

```java
@Repository
public interface DepartmentRepository 
        extends JpaRepository<Department, Long> {


    @EntityGraph(
        attributePaths = {"employees"}
    )
    List<Department> findAll();

}
```

Now Hibernate generates:

```sql
SELECT 
    d.id,
    d.name,
    e.id,
    e.name
FROM department d
LEFT JOIN employee e
ON d.id = e.department_id;
```

Instead of:

```
1 query for department
+
N queries for employees
```

Now:

```
1 query
```

## EntityGraph Flow

Without EntityGraph:

```
Department Query

      |
      v

Access employees

      |
      v

Employee Query
Employee Query
Employee Query
```

With EntityGraph:

```
Department Query

      |
      v

Department + Employees
(single query)
```

# Types of EntityGraph

## Named EntityGraph

Define on Entity:

```java
@Entity
@NamedEntityGraph(
    name = "Department.employees",
    attributeNodes = {
        @NamedAttributeNode("employees")
    }
)
public class Department {

}
```

Use in repository:

```java
@EntityGraph(
    value = "Department.employees"
)
List<Department> findAll();
```

## Adhoc EntityGraph

Define directly in repository:

```java
@EntityGraph(
    attributePaths = {
        "employees"
    }
)
List<Department> findAll();
```

Usually preferred for simple cases.

# Multiple Relationships with EntityGraph

Example:

```
Department
    |
    +-- Employees
    |
    +-- Projects
```

Repository:

```java
@EntityGraph(
    attributePaths = {
        "employees",
        "projects"
    }
)
List<Department> findAll();
```

Generated SQL:

```sql
SELECT *
FROM department d
LEFT JOIN employee e
LEFT JOIN project p;
```

# EntityGraph Limitations

## Multiple Collection Fetch Problem

Example:

```java
Department
 |
 +-- employees
 |
 +-- projects
```

Both:

```java
@OneToMany
```

Fetching both may cause:

```
MultipleBagFetchException
```

because Hibernate cannot efficiently create multiple bag joins.

Solution:

- Use DTO projection
- Fetch separately
- Use batch fetching

# Solution 2: DTO Projection

## What is DTO Projection?

Instead of loading full entities, fetch only the required data into a custom object.

Example:

Instead of:

```
Department Entity
        |
        +-- Employee Entity
```

Load:

```
DepartmentDTO
        |
        +-- EmployeeDTO
```

## DTO Classes

Department DTO:

```java
public class DepartmentDTO {

    private Long id;

    private String name;

    private List<EmployeeDTO> employees;

}
```

Employee DTO:

```java
public class EmployeeDTO {

    private Long id;

    private String name;

}
```

# DTO Query Using JPQL

Repository:

```java
@Query("""
SELECT new com.example.DepartmentDTO(
    d.id,
    d.name
)
FROM Department d
""")
List<DepartmentDTO> findDepartments();
```

Hibernate generates:

```sql
SELECT
    id,
    name
FROM department;
```

Only required columns are fetched.

# DTO with Join

Example:

```java
@Query("""
SELECT new com.example.EmployeeDTO(
    e.id,
    e.name,
    d.name
)
FROM Employee e
JOIN e.department d
""")
List<EmployeeDTO> findEmployees();
```

SQL:

```sql
SELECT
    e.id,
    e.name,
    d.name
FROM employee e
JOIN department d;
```

# EntityGraph vs DTO

| Feature | EntityGraph | DTO Projection |
|---|---|---|
| Returns | Entity objects | Custom objects |
| Fetch control | Association based | Column based |
| Performance | Good | Usually better |
| Memory usage | Higher | Lower |
| Updates possible | Yes | No |
| Best for | Entity operations | Read-only APIs |

# When to Use EntityGraph

Use EntityGraph when:

- You need entities
- You need relationships
- You may update data later
- Object graph is small

Example:

```
Order
 |
 +-- Customer
```

API needs complete order object.

Use:

```java
@EntityGraph(
    attributePaths = {"customer"}
)
```

# When to Use DTOs

Use DTOs when:

- Building REST APIs
- Returning reports
- Large datasets
- Only few fields are required

Example:

Database:

```
Employee

id
name
salary
address
phone
department
```

API needs:

```
name
department
```

DTO avoids loading unnecessary fields.

# Alternative: Batch Fetching

Hibernate can load collections in batches.

Configuration:

```properties
spring.jpa.properties.hibernate.default_batch_fetch_size=50
```

Instead of:

```
Employee query
Employee query
Employee query
```

Hibernate creates:

```sql
SELECT *
FROM employee
WHERE department_id IN (1,2,3,4,5);
```

# Best Practices

## Avoid FetchType.EAGER

Bad:

```java
@OneToMany(
    fetch = FetchType.EAGER
)
```

Problems:

- Loads unnecessary data
- Can create huge joins
- Can still cause performance issues

Prefer:

```java
fetch = FetchType.LAZY
```

and control fetching explicitly.

## Use EntityGraph for Simple Object Fetching

Example:

```
Order
 |
 +-- Customer
```

## Use DTOs for API Responses

Example:

```
REST Controller
       |
       v
DTO
       |
       v
Database
```

# Interview Summary

```
N+1 problem occurs when Hibernate executes one query to fetch parent
records and additional queries for each child record.

Example:
1 query for Departments
+
N queries for Employees

EntityGraph solves it by explicitly telling Hibernate which relationships
to fetch using JOIN.

DTO projection solves it by fetching only required columns instead of
loading complete entities.

Use EntityGraph when you need entities.
Use DTOs when you need optimized read-only responses.
```

## One-Line Interview Answer

> N+1 is a Hibernate performance issue caused by lazy loading where one query fetches parent entities and additional queries fetch each child entity. EntityGraph avoids it by controlling fetch plans, while DTO projections avoid it by selecting only the required data directly from the database.

# JPA EntityGraph with Subgraphs (Nested Relationships)

## What is a Subgraph in EntityGraph?

A `Subgraph` is used when you want to fetch **nested relationships** inside an EntityGraph.

A normal EntityGraph fetches direct relationships:

```
Department
    |
    +-- Employees
```

A Subgraph fetches relationships inside those relationships:

```
Department
    |
    +-- Employees
            |
            +-- Address
```

Without subgraph:

```
Department
    |
    +-- Employees
            |
            +-- Lazy Address Query
```

With subgraph:

```
Department
    |
    +-- Employees
            |
            +-- Address
```

Everything is fetched together.

# Example Domain Model

## Department Entity

```java
@Entity
@NamedEntityGraph(
    name = "Department.employeeDetails",
    attributeNodes = {
        @NamedAttributeNode(
            value = "employees",
            subgraph = "employee-subgraph"
        )
    },
    subgraphs = {
        @NamedSubgraph(
            name = "employee-subgraph",
            attributeNodes = {
                @NamedAttributeNode("address")
            }
        )
    }
)
public class Department {

    @Id
    private Long id;

    private String name;


    @OneToMany(
        mappedBy = "department",
        fetch = FetchType.LAZY
    )
    private List<Employee> employees;

}
```

## Employee Entity

```java
@Entity
public class Employee {

    @Id
    private Long id;

    private String name;


    @ManyToOne(
        fetch = FetchType.LAZY
    )
    private Address address;


    @ManyToOne
    private Department department;

}
```

## Address Entity

```java
@Entity
public class Address {

    @Id
    private Long id;

    private String city;

    private String country;

}
```

# Understanding the EntityGraph

This part:

```java
@NamedAttributeNode(
    value = "employees",
    subgraph = "employee-subgraph"
)
```

means:

```
Fetch Department.employees
        |
        v
Use employee-subgraph
```

Then:

```java
@NamedSubgraph(
    name = "employee-subgraph",
    attributeNodes = {
        @NamedAttributeNode("address")
    }
)
```

means:

```
Employee
    |
    +-- Fetch Address
```

Final fetch graph:

```
Department

   |
   |
 Employees

   |
   |
 Address
```

# Using Named EntityGraph in Repository

```java
@Repository
public interface DepartmentRepository 
        extends JpaRepository<Department, Long> {


    @EntityGraph(
        value = "Department.employeeDetails"
    )
    List<Department> findAll();

}
```

Hibernate now knows:

```
Department
    |
    +-- Employees
            |
            +-- Address
```

should be fetched.

# Adhoc EntityGraph with Subgraph

Instead of annotations, you can define it dynamically.

Example:

```java
@EntityGraph(
    attributePaths = {
        "employees",
        "employees.address"
    }
)
List<Department> findAll();
```

Spring Data JPA converts:

```
employees.address
```

into a nested fetch graph.

For simple cases this is enough.

# Multiple Levels of Subgraphs

Example:

```
Department
    |
    +-- Employees
            |
            +-- Projects
                    |
                    +-- Client
```

EntityGraph:

```java
@NamedEntityGraph(
    name = "Department.fullDetails",
    attributeNodes = {
        @NamedAttributeNode(
            value = "employees",
            subgraph = "employeeGraph"
        )
    },
    subgraphs = {

        @NamedSubgraph(
            name = "employeeGraph",
            attributeNodes = {
                @NamedAttributeNode(
                    value = "projects",
                    subgraph = "projectGraph"
                )
            }
        ),

        @NamedSubgraph(
            name = "projectGraph",
            attributeNodes = {
                @NamedAttributeNode("client")
            }
        )
    }
)
```

Result:

```
Department

    |
    +-- Employees

            |
            +-- Projects

                    |
                    +-- Client
```

# EntityGraph vs JOIN FETCH

Both solve N+1 problems.

## JOIN FETCH

JPQL:

```java
@Query("""
SELECT d
FROM Department d
JOIN FETCH d.employees
""")
List<Department> findDepartments();
```

Advantages:

- Simple
- Explicit SQL control

Disadvantages:

- Query changes required
- Harder to reuse

## EntityGraph

Repository:

```java
@EntityGraph(
    attributePaths = {
        "employees"
    }
)
List<Department> findAll();
```

Advantages:

- Reusable
- Keeps query clean
- Dynamic fetch plans

# Important EntityGraph Types

## Fetch Graph

```java
EntityGraphType.FETCH
```

Meaning:

```
Only attributes mentioned in graph are fetched eagerly.
Other relationships remain lazy.
```

Example:

Graph:

```
Department
 |
 Employees
```

Result:

```
Employees loaded
Projects remain lazy
```

## Load Graph

```java
EntityGraphType.LOAD
```

Meaning:

```
Attributes in graph become eager.
Other mappings keep their default fetch type.
```

Example:

Entity:

```java
@ManyToOne(fetch = FetchType.EAGER)
private Manager manager;
```

Graph:

```
Department
 |
 Employees
```

Result:

```
Employees loaded
Manager also loaded because it is EAGER
```

# Common Problems with EntityGraph

## Multiple Collections

Example:

```
Department
 |
 +-- Employees
 |
 +-- Projects
```

Trying:

```java
@EntityGraph(
    attributePaths = {
        "employees",
        "projects"
    }
)
```

may cause:

```
MultipleBagFetchException
```

Reason:

Hibernate cannot efficiently join multiple `List` collections.

Solutions:

- Convert List to Set
- Use DTO projection
- Fetch separately
- Use batch fetching

# EntityGraph + Pagination Issue

Example:

```java
Page<Department> findAll(Pageable pageable);
```

with:

```java
employees
```

may produce incorrect pagination because joins duplicate rows.

Example:

Database:

```
Department 1
   Employee A
   Employee B
```

Join result:

```
Department 1 Employee A
Department 1 Employee B
```

Hibernate must remove duplicates in memory.

For large data:

Prefer:

1. Fetch IDs first
2. Fetch details using EntityGraph

# Interview Summary

```
EntityGraph defines a fetch plan for JPA entities.

A normal EntityGraph fetches direct relationships.

A Subgraph is used to fetch nested relationships.

Example:

Department
    |
    +-- Employees
            |
            +-- Address

The EntityGraph fetches the entire object graph in a controlled way
and prevents N+1 query problems caused by lazy loading.

Use EntityGraph for entity-based operations and DTO projections for
optimized read-only API responses.
```

## One-Line Interview Answer

> JPA EntityGraph controls which associations Hibernate should fetch eagerly for a specific query. Subgraphs allow fetching nested associations, avoiding N+1 problems for complex object relationships without changing the entity fetch type globally.
